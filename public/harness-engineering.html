Harness Engineering

A powerful model is only half an agent. The harness is what turns raw intelligence into code you can trust.

Objective of this article

By the end, you'll understand the five parts of a harness, see how they work together in one loop, and have a step-by-step plan to build a simple harness for your own repo.

Step 1: Understand what a harness is

Let's start simple. Why does the same AI model write great code in one tool and messy code in another?

The answer is the harness: everything built around the model. The model thinks. The harness tells it the rules, gives it hands, gives it a safe workspace, helps it remember, and tells it when it's wrong.

A simple way to picture it

  • The model is the engine. Powerful, but it can't drive anywhere on its own.
  • The harness is the car. Steering, brakes, dashboard and road rules.
  • Harness engineering is the job of building that car so the engine gets you somewhere safely.

Step 2: Learn the five parts

Every good harness has the same five parts. Let's take them one at a time.

1

Instructions: tell it the rules

The agent needs to know how your project works. You write this down once in a file like AGENTS.md.

  • What goes in: project overview, test commands, coding style, and what "done" means.
  • Example: "Run tests with npm test. Never edit /migrations."
2

Tools: give it hands

A model can only talk. Tools let it act: read files, edit code, run commands, search the web.

  • Example: Claude Code can read your repo, edit a file and run pytest on its own.
  • Key idea: give only the tools the task needs. Fewer tools means fewer mistakes.
3

Environment: give it a safe workspace

The agent works in a sandbox, a separate space where mistakes can't hurt your real project.

  • Examples: a Git branch or worktree, a Docker container, or GitHub Codespaces.
  • Key idea: you review the changes, then decide what reaches your main branch.
4

State: help it remember

Agents forget when a session ends or the context fills up. State is the agent's notebook.

  • Example: a progress.md file listing what's done, what's next, and any open problems.
  • Key idea: the next session reads the notebook and continues, instead of starting from zero.
5

Feedback: tell it when it's wrong

The agent needs a clear signal of pass or fail. Without it, it guesses.

  • Examples: test results, linter errors, type checks, and CI checks on GitHub.
  • Key idea: "2 tests failed" is far more useful to an agent than "looks fine to me."

Step 3: See how the parts work together

The five parts aren't a checklist. They form a loop the agent runs again and again until the work is done.

Walk through one lap

  • Read: the agent opens AGENTS.md and learns tests run with npm test.
  • Act: it writes a new login function inside a Git worktree.
  • Check: it runs the tests and sees "1 test failed: empty password accepted."
  • Save: it notes "login works, fix empty-password check" in progress.md.
  • Repeat: it fixes the check, runs tests again, and everything passes. Done.

Step 4: Build your first harness

Now let's build one for a real repo. You need about 30 minutes and four small files or settings.

4.1 Write the rules file

Create AGENTS.md in your repo root. Keep it short and specific.

# AGENTS.md

## Project
Payroll API. Node + Express + PostgreSQL.

## Commands
- Install: npm install
- Test: npm test
- Lint: npm run lint

## Rules
- Use TypeScript strict mode.
- Never edit /migrations without asking.
- Every new route needs a test.

## Done means
Tests pass, lint is clean, PR explains the change.

4.2 Connect Claude Code to it

Claude Code reads CLAUDE.md. Make it one line that points to your rules, so every agent shares one source of truth.

# CLAUDE.md
@AGENTS.md

4.3 Give the agent a sandbox

Don't let the agent work directly on main. The easiest option is a Git worktree:

git worktree add ../myapp-agent -b agent/login-feature
cd ../myapp-agent

Prefer the cloud? Open the repo in GitHub Codespaces instead. Free accounts get about 60 hours a month on a 2-core machine.

4.4 Add a state file

Create progress.md and ask the agent to update it at the end of every session.

# progress.md
## Done
- Login route created
## Next
- Add password reset
## Open problems
- Empty password is accepted

4.5 Make feedback automatic

Tests are your strongest feedback. Add a GitHub Actions check so every change gets tested, whether a human or an agent wrote it.

# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
Quick win: if your project has no tests yet, ask the agent to write tests first. A harness without feedback is a car without a dashboard.

GitHub Actions: Automatic Testing for Every Change

Tests only help if someone runs them. GitHub Actions makes sure they run every single time.

What is it?

GitHub Actions is a free robot built into GitHub. It runs commands for you whenever something changes in your repo.

  • A check is one job the robot runs, like "run the tests."
  • Each check ends with a clear result: pass ✅ or fail ❌.

How it works in 3 steps

  • 1. Add the file. Create .github/workflows/test.yml in your repo.
  • 2. Push your code. GitHub runs your tests on every push.
  • 3. Read the result. You see ✅ or ❌ next to the change.

Example workflow for Node

# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test

The Python version

# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt
      - run: pytest

Why it matters for AI agents

  • It is automatic feedback. The agent doesn't have to remember to test.
  • It catches broken code before it reaches main.
  • A ❌ gives the agent a concrete problem to fix, instead of a guess.
Remember: the robot doesn't care who wrote the code. Human or agent, every change gets the same test.

Step 5: Learn from real products

The big coding agents all use these same five parts, but each one makes different choices. Here's a quick map based on the Learn Harness Engineering course on GitHub.

ProductWhat stands out in its harness
Claude CodeLayered memory, context compaction for long sessions, hooks, and isolated sub-agents.
CodexThe repository as source of truth, AGENTS.md as a directory page, and worktree isolation.
PiA minimal core that you expand with your own programmable additions.
DeepSeek"Everything is a plugin," with clear extension points and an event pipeline.

Inside Claude Code's harness

The Claude Code row lists four ideas. Here is what each one means.

1Layered memory

Claude reads CLAUDE.md files at different levels and combines them.

  • User level (~/.claude/CLAUDE.md): your personal rules for every project
  • Project level (CLAUDE.md in the repo): team rules, shared via Git
  • Folder level: extra rules for one part of the code

Example: "Reply in short answers" goes in your user file, and "Run pytest" goes in the project file.

2Context compaction

In a long session, the chat fills Claude's memory window. Claude then summarises the older parts so it can keep going without losing the thread.

Example: after two hours of work, /compact shrinks the history to the key decisions and files changed.

3Hooks

Commands that run automatically at set moments, such as before or after Claude edits a file.

Example: after every edit, a hook runs your formatter or tests automatically.

4Isolated sub-agents

Claude hands a side task to a helper agent with its own clean memory. The helper does the work and sends back only a short result.

Example: a "code reviewer" sub-agent checks your changes without cluttering the main conversation.

The lesson: you don't need to copy any one product. Pick the ideas that fit your project size and your team.

Step 6: Avoid the common mistakes

  • A giant rules file. 500 lines of rules gets skimmed. Keep the essentials and link to longer docs.
  • No tests. Without feedback, the agent can't tell broken code from working code.
  • Working on main. One bad command can damage your real project. Always use a sandbox.
  • No memory between sessions. Without a state file, every session starts from zero.
  • Too many tools. Every extra tool is another way to go wrong. Add tools only when needed.

Your harness checklist

Tick these off and your repo is ready for AI coding agents.

  • AGENTS.md with commands, rules and a definition of done
  • CLAUDE.md pointing to @AGENTS.md
  • Sandbox set up: worktree, branch, Docker or Codespaces
  • progress.md updated at the end of each session
  • Tests + CI running on every push
Remember: better models will keep arriving. A good harness makes every one of them work better in your project, from day one.

Your Questions Answered

Quick answers to the questions people ask most, each with one practical example.

1What is AGENTS.md?

A file in your repo root that tells every AI coding agent how your project works. You write it once, and Claude Code, Codex and Copilot can all follow it.

Example: Run tests: npm test. Never edit /migrations.

2AGENTS.md vs CLAUDE.md

AGENTS.md is the shared rulebook for all agents. CLAUDE.md is Claude Code's own file.

# AGENTS.md
Run tests: npm test
Use TypeScript.

# CLAUDE.md
@AGENTS.md

3One line that points to your rules

CLAUDE.md holds only @AGENTS.md. The @ tells Claude to load that file, so all your rules live in one place.

Example: you add "Use Python 3.12" to AGENTS.md, and Claude, Codex and Copilot all pick it up instantly.

4Environment and Feedback

Environment is where the agent works. Feedback tells it whether it succeeded.

Example: the agent edits code in a sandbox, runs npm test, sees "2 tests failed," and fixes them.

5Sandbox and main project

Your main project is your original working code, usually the main branch. A sandbox is a separate space where the agent can't damage it.

  • Git branch or worktree: a separate copy of your code
  • Docker container: a mini computer inside your computer
  • Cloud sandbox: a remote machine, like Codespaces

6Codex and GitHub Codespaces

Codex is OpenAI's coding agent. Codespaces is GitHub's cloud computer with VS Code in your browser.

Example: open any repo, click Code → Codespaces, and start coding with nothing installed.

7Is Codespaces free?

Yes, with limits. Free accounts get 120 core hours (60 hours on a 2-core machine) and 15 GB storage per month. After that, a 2-core machine costs $0.18/hour.

Example: without a payment method, it simply stops when free hours run out, so there's no surprise bill.

8How to benefit from Codespaces

  • Code from any device
  • Test agents safely
  • Same setup every time with a .devcontainer file
  • Run heavy builds on GitHub's machine instead of your laptop

Example: Repo → Code → Codespaces → Create codespace on main. Stop it when you're done to save hours.

9Can Codespaces host an always-on agent?

No. It stops after about 30 minutes idle, so it's for building, not hosting.

Better hosting options:

  • Hugging Face Spaces: free demos
  • Render / Railway: always-on APIs
  • Google Cloud Run: pay per use
  • VPS: full control, runs 24/7
